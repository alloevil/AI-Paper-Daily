| # | 篇名 | Diátaxis 类型 | 核心内容 |
|---|------|-------------|---------|

## 二、核心原则

### 2.1 忠于官方文档（最高优先级）

- 所有技术内容**必须有官方文档出处**
- 不编造 API、不猜测行为
- 不确定的标 `[待验证]`
- 每篇完成后自查：每个 API、参数、行为描述 → 回溯到文档原文

### 2.2 内容来源权重

| 来源 | 权重 | 说明 |
|------|------|------|
| 官方文档 hermes-agent.nousresearch.com | 主干 | 框架、API、配置项等事实性内容 |
| GitHub repo NousResearch/hermes-agent | 补充 | 源码、Issue、CHANGELOG 中的实操细节 |
| 横向对比 OpenClaw | 加分项 | 降低认知成本，仅在有出处的对比时使用 |

### 2.3 抓取策略

- `web_fetch` 设 `maxChars=50000`，确保不截断
- 超长页面分多次抓取
- JS 渲染页面用 `firecrawl_scrape` 备用
- 文档源码在 GitHub 时直接读 mdx 文件

## 三、Diátaxis 分型写作规则

### Tutorial（教程篇）— 第 1、2 篇

- **目标**：读者跟着做，5 分钟内跑通第一个示例
- **语气**：引导式，"跟我做"，像教练带学员
- **核心要求**：
  - 第一个示例必须是**最短路径**（minimal viable example）
  - 每一步都是可执行命令，不给伪代码
  - 失败了怎么办？给出常见错误和修复方法
  - Tutorial 的目标是**学会技能**，不是完成任务
- **禁止**：塞入太多解释（解释内容链接到 Explanation 页面）

### How-to Guide（操作指南篇）— 第 3、4、5 篇

- **目标**：帮有经验的用户完成具体任务
- **语气**：直接、实用，"要完成 X，这样做"
- **核心要求**：
  - 假设读者已有基础（不教安装、不解释概念）
  - 每个指南解决一个真实场景
  - 可以有多种路径到达同一目标
- **禁止**：从头教学、解释"为什么"

### Explanation（解释篇）— 第 6 篇

- **目标**：帮读者理解架构和设计原理
- **语气**：可以有观点，可以多角度讨论
- **核心要求**：
  - 回答"为什么"而不是"怎么做"
  - 可以包含设计取舍、架构对比
  - 链接到 Tutorial/How-to 作为实操入口
- **禁止**：混入操作步骤（步骤应该链接到 How-to）

## 四、格式规范

### 4.1 每篇结构

```markdown
# 篇名

> 一句话说明这篇解决什么问题。

**前置要求**：xxx
**预计时间**：xxx
**官方文档**：[链接]

## 你将学到
- 要点 1
- 要点 2
- ...

## 正文（按需分节）

## 下一步
- 推荐阅读：[下一篇名](链接)
```

### 4.2 命令格式

- 标明执行环境：`# 本地终端` / `# Docker 容器` / `# 远程服务器`
- 带完整路径，不省略
- 输出结果用 ` ``` ` 代码块包裹
- 长命令拆行用 `\`

### 4.3 对比表格

OpenClaw 对比用 `|` 表格，格式：

| 功能 | Hermes Agent | OpenClaw |
|------|-------------|----------|
| xxx | 行为 A | 行为 B |

### 4.4 术语

- 保留英文专有名词：Memory、Session、Tool、Skill、MCP、Cron
- 不硬翻译：不叫"记忆模块""会话管理器"
- 中文叙述中首次出现加括号英文

## 五、质量检查清单

每篇完成后逐项过：

- [ ] 第一个示例 5 分钟内能跑通
- [ ] 所有命令可直接复制执行
- [ ] 每个 API/参数能追溯到官方文档出处
- [ ] 不确定内容标了 `[待验证]`
- [ ] 每篇开头有"你将学到"，结尾有"下一步"
- [ ] 交叉引用其他篇时附链接
- [ ] 版本号标注（基于当前稳定版）
- [ ] 无拼写/格式错误

## 六、版本锁定

- 基于 Hermes Agent 当前稳定版写作
- 每篇末尾标注 `本文基于 Hermes Agent vX.Y.Z`
- 官方文档更新后需同步修订
